RAG systems have a similar problem, but with a twist: **find the chunks closest in meaning to this query**. Not exact matches. Not alphabetical sorting. *Meaning*.

You can't B-Tree your way through that. "Meaning" doesn't sort alphabetically. So vector databases use a completely different family of indexes built specifically for high-dimensional similarity search. Same goal as a B-Tree (skip 99% of the data), different shape entirely.

Let me show you why vector indexing is critical to making RAG work.

## The problem: searching through meaning

RAG (Retrieval-Augmented Generation) systems work by breaking documents into smaller pieces called **chunks**, turning those chunks into numerical representations called **embeddings**, and then finding the most relevant chunks when a user asks a question.

Here's the challenge: you might have millions of chunks. When a user asks "how do I cancel my subscription?", you need to find the 3-5 most relevant chunks out of those millions in milliseconds.

If you compared the user's question to every single chunk one by one, it would take 2+ seconds per search. Unusable.

This is where **vector indexing** comes in.

## Quick context: chunking and embeddings

**Chunking:** Split documents into 500-800 token pieces so they fit in the LLM's context window. Use 10-15% overlap to prevent losing context at boundaries.

To compare embeddings, we use **cosine similarity** (measures the angle between vectors). Small angle = similar meaning.

Now here's the key question: how do you find the most similar vectors quickly when you have millions of them?

## Why traditional indexes don't work for vectors

B-Trees work by sorting data. You can find `email = 'a@b.com'` quickly because emails are sorted alphabetically.

But vectors representing meaning can't be sorted. There's no "alphabetical order" for concepts. "Dog" isn't "before" or "after" "cat". They're just *near each other* in meaning-space.

This is why vector search needs a completely different approach.

## Vector indexes: HNSW

The most popular solution is **HNSW** (Hierarchical Navigable Small World). It's a graph-based index designed for high-dimensional similarity search.

The core idea: build a graph where each vector is a node connected to its closest neighbors. Add multiple layers. The top layer is a sparse "highway" with long-distance shortcuts. The bottom layer connects everything densely.

When you search, you start at the top layer, hop to the nearest neighbor, drop down a layer, hop again, and repeat. Each hop gets you closer. You never check most of the vectors, just the ones along the path.

Think of it like a highway system. Start on the interstate (top layer), take big jumps between cities. Exit to a state highway (middle layer), get closer. Finally, local roads (bottom layer) to the exact address.

With 1 million vectors, HNSW checks only ~200 of them to find the best match. That's a 5000x reduction. This is why vector search is fast enough for real-time use.

## Building a vector index

In Postgres with pgvector:

```sql
CREATE TABLE chunks (
    id BIGSERIAL PRIMARY KEY,
    content TEXT,
    embedding VECTOR(1536)
);

CREATE INDEX ON chunks USING hnsw (embedding vector_cosine_ops);
```

That `CREATE INDEX` line does the same job as indexing in traditional databases, just with a graph structure instead of a tree. Without it, every query scans every row. With it, searches take milliseconds.

**Without indexing:** 1 million chunks = 1 million comparisons per query. Result: 2+ seconds per search.

**With HNSW indexing:** 1 million chunks = ~200 comparisons per query. Result: 5-10 milliseconds per search.

Vector indexing is what makes RAG viable in production. Same fundamental problem as database indexing (skip the data you don't need), different data structure (graphs instead of trees).

## Important gotchas

**Approximate vs exact search:** HNSW returns *approximate* nearest neighbors. You might miss the true best match 5% of the time. For RAG, this is usually fine. The speed gain is worth it.

**Index build time:** Building an HNSW index on 1 million vectors takes 10-30 minutes. On 10 million, it could take hours. Run it as a background job.

**Can't change embedding models:** A vector from `text-embedding-3-small` can't be compared to one from `bge-base`. Different model = different coordinate system. Switching means re-embedding everything and rebuilding the index. Pick your model carefully.

**Chunk size matters:** Too small (200 tokens) loses context. Too big (2000 tokens) dilutes the embedding. Start at 500-800 tokens.

## The big picture

A RAG system is a search engine with an LLM on top. Vector indexing solves the search part.

Just like B-Trees made databases practical by making queries fast, HNSW makes RAG practical by making similarity search fast. Same core idea (skip what you don't need), different data structure (graphs instead of trees), different problem (meaning instead of sorting).

Vector indexing is the unsung hero. Without it, RAG would be too slow to use. With it, you can search millions of chunks in milliseconds.
